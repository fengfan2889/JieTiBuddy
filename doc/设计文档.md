## 项目概述

- **项目名称**: 解题伙伴（JieTiBuddy）
- **创建日期**: 2026-09-14
- **项目路径**: `F:\jyw\study\android\JieTiBuddy`
- **项目描述**: 面向高中生的拍照解题 AI 应用。学生拍照上传不会做的题目，AI 通过**多轮启发式提问**引导其自行解出，而不是直接给答案。

### 核心价值主张

> **教会思考，而不是代写作业。**
> **但不能让孩子干想——卡住时，思路必须给足。**

这两句话不是文案，而是**架构约束**：

- 任何绕过「不直接给答案」的实现方式（例如默认模式直出解析）都属于需求走偏，必须重新评审。
- 任何把"我再想想"当作引导的实现方式，同样属于需求走偏。
  学生卡住时他要的是**分析 + 解题思路**。只反问不给信息，孩子会丧失兴趣直接关掉应用。
  这条红线由用户明确提出，已落成 D11 与风险 R11 的三层防护（提示词红线 / 后置黑名单校验 / 模板化降级）。

### 目标用户

| 角色 | 描述 | 关注点 | 版本 |
|------|------|--------|------|
| 学生（主） | 高中生，数理化为主 | 看懂题、**拿到思路**、不要被直接给答案、不要被晾着干想 | MVP |
| 家长（辅） | 购机/付费决策者，即项目发起人 | 学习过程可见、不被当作抄答案工具 | Phase 3 |

### 业务目标（可衡量）

| 编号 | 目标 | 衡量方式 |
|------|------|----------|
| G1 | 题目识别准确率 | 数学题干 OCR 准确率 ≥ 95%；公式转 LaTeX 可用率 ≥ 90% |
| G2 | 引导有效性 | ≥ 70% 的会话在 5 轮引导内由学生自己给出关键步骤 |
| G3 | 不越界 | 「引导模式」下 AI 直接吐完整答案的比例 = 0（可用自动化测试断言） |
| G4 | 高频可用 | 单次拍照 → 首条引导回复 P95 延迟 ≤ 8s |
| **G5** | 🔴 **不空泛** | 命中空泛话术黑名单（"你再想想"等）的回复比例 = 0；每一轮回复都含实质信息（自动化断言，T15~T18） |
| **G6** | 有效帮助 | 学生表示"不会"后，**下一轮回复必定包含该步的分析或思路**；单题平均引导轮次 ≤ 6 |

## 技术栈

### ✅ 已确认方案（方案 A：单代码库 Web + Capacitor 多端）

| 层 | 选型 | 版本基线 | 选型理由 |
|----|------|----------|----------|
| 前端 | React + TypeScript + Vite | React 18 / TS 5.x / Vite 5 | 生态成熟，HMR 快，TS 强类型便于与后端共享类型 |
| 样式 | Tailwind CSS | 4.x | 移动端优先、原子化，避免手写 CSS 分裂 |
| 端壳 | Capacitor | 6.x | 一套 Web 代码打包成 Android APK，后续直接加 iPad / macOS target |

| 后端 | Node.js + Fastify + TypeScript | Node ≥ 22.13 / Fastify 5 | 与前端同语言，共享类型；Fastify 性能与 SSE 支持好 |

| ORM | Drizzle ORM | latest | 轻量、TS 友好、迁移可版本化，且 SQLite/PG 双支持 |
| AI 模型 | 多模态大模型（见 D2） | — | 图片直读 + 多轮对话是硬需求 |
| 校验 | Zod | 3.x | 接口入参校验 + 共享类型推导 |
| 日志 | pino | latest | 结构化日志，含 stacktrace（符合全局日志规范） |
| 包管理 | npm workspaces | 10.x | monorepo：`web` / `server` / `shared` 三包（环境里没有 pnpm，用 npm 内置 workspaces 零额外安装） |
| 测试 | Vitest + Playwright | latest | 提示词约束用 Vitest 做断言，端到端用 Playwright |

### 整体架构

```

│  ┌────────────┐  ┌──────────────┐  ┌───────────────────┐    │

│  │ problems   │─▶│ tutor-engine │─▶│ qwen / openai /…  │    │
│  │ sessions   │  │ (状态机)      │  └───────────────────┘    │

│         │               │                                    │
```

### 关键设计点

1. **引导引擎（tutor-engine）是有状态的**，不是"无脑转发给大模型"。
   会话保存 `plan`（引导地图）、`currentRoute`、`supportLevel`、`studentState`、`stepIndex`，
   每轮把结构化状态拼进提示词，才能做到"根据学生回答动态调整支持强度"。
   **分析与引导分离**（D10）：分析只做一次并产出引导地图，对话轮只做"取用 + 改写"。
   **每步的 `analysis` / `approach` 是 S0 的默认输出**（D11）——这是从结构上杜绝空泛回复的关键设计。
2. **Provider 抽象层**隔离模型厂商。统一接口 `chat(messages, images) → stream`，
   换供应商只改配置，业务代码零改动。
3. **OCR 走多模态模型直读，不做独立 OCR 服务**。识别结果作为"可编辑文本"落库（`ocr_text` / `ocr_latex`），
   学生可修正——修正后的文本才是后续对话的唯一依据。
4. **图片生命周期**：原图压缩到 ≤ 1600px 长边、JPEG q80 后上传；
   MVP 原图只存本地沙盒路径，服务端默认只存文本与缩略图，避免存储与隐私成本。
5. **流式输出**：引导回复用 SSE 逐字返回，降低"等待焦虑"，符合 G4。

## 核心模块

| 模块 | 职责 | 关键约束 |
|------|------|----------|
| **capture**（前端） | 调起相机/相册，裁剪、压缩、预览 | 安卓需 `CAMERA` 权限；Web 降级为 file input |
| **ocr**（前后端） | 多模态模型识别题干与公式，输出 `text` + `latex` | 识别结果必须**可编辑**，学生修正后覆盖原值 |
| **analyze**（前端展示） | 输出学科、知识点、难度，以及是否给「直接看答案」选项 | 分析结果对用户可见，但不含答案 |
| **tutorEngine**（核心） | 引导状态机：每轮判断学生状态 → 从引导地图取对应支持强度(S0~S3) → 生成引导语 | 🔴 引导模式永不输出最终答案；🔴 **学生说"不会"必须给分析+思路，禁止空泛反问**（D11）；进度只走一小步 |
| **summarize** | 题目解决后生成完整解析、知识点、易错点 | 仅在 `session.status = solved` 后触发 |
| **Provider 层** | 统一多家多模态模型的调用与流式返回 | 业务层不出现任何厂商专有字段 |
| **session store** | 会话持久化与历史回放 | 图片与文本分离存储，文本是唯一上下文来源 |

### tutorEngine 状态机（核心）

学生状态（`student_state`）与支持强度（`support_level`）的映射：

| 学生状态 | 判定依据 | 下一步动作 | support_level 变化 |
|----------|----------|-----------|------------------|
| `CORRECT` | 回答与标准解一致 | 具体肯定对在哪里 + 把下一步方向交给他 | ↓1（回到 S0） |
| `PARTIAL` | 方向对但不完整 | 指出缺的那一块 | 保持 S0/S1 |
| `WRONG` | 明确出错 | 不否定人，指出**具体错因**（符号/条件/单位/概念） | ↑1 |
| `STUCK` | 「不知道」「不会」「看不懂」 | 🔴 **直接给分析 + 解题思路**，再给一个具体小动作 | 从 S0 起步，逐级升 |
| `ASK_WHY` | 「为什么这步要这么做」 | **正面回答原因**，不许反问回去 | → S1 |
| `OFF_TRACK` | 答非所问 | 先用大白话复述题目要求，再给思路 | 保持 S0 |
| `WANTS_ANSWER` | 「直接告诉我答案」 | 先给足分析与思路（这是必须给的，不是交换条件），再说明为什么不给最终结论 | 从 S1 起步，逐级升 |
| `SOLVED` | 关键步骤全部完成 | 进入 `summarize` | — |

`support_level` 分 4 档（v0.3 重构，原 L0~L4 五档废弃）：

```
S0 分析 + 解题思路   ← 默认档，必须给足，不是"最低限度的敷衍"
     ① 这一步在考什么、为什么这么做  ② 这一步该怎么下手（方向 + 为什么这个方向）
S1 思路 + 具体方法   点明用哪个公式/定理，并说明怎么套进去
S2 方法 + 算式结构   把算式摆出来，把待求的量留成空位，学生只算最后一小步
S3 单步演示         完整演示当前这一步的推理与中间结论，结尾立刻停在提问上
```

> 🔴 红线一：**S3 只演示"当前一步"，绝不连续演示到答案。** 已解出的步数 ≥ 总步数时才能进入总结。
>
> 🔴 红线二（v0.3 新增）：**禁止空泛提示**。`support_level` 再低也不等于"少给信息"——
> "你再想想"、"仔细读题"、"先自己试试"、"动动脑筋"、无铺垫的空反问一律判不合格，
> 由后置黑名单校验拦截并重生成（对应风险 R11）。
>
> 🔴 红线三：**"一次只走一小步"指进度，不指信息量。**
> 学生读完每一轮回复，都应该知道这一步**该怎么下手**，但这一步的**结果仍需他自己算**。

## 交互设计（已确认）

### 完整交互流程

```
① 拍照 / 相册 —— 🔴 **取图即识别**（D23）：拍完/选完这一张就开始读题，
      图上压一层进度遮罩，屏幕上只有「重拍」一个按钮；
      识别失败才多出一个「重新识别」，成功则直接进确认页（中间不再有确认点击）
      ↓
② OCR 识别 → 展示识别结果 → 学生可手动修正（Phase 2）
      ↓
③ AI 分析：学科 / 知识点 / 难度 / 解题步骤骨架 plan
      🔴 这一组元信息（学科 / 难度 / 年级 / 知识点 / 读题模型）从确认页**一路带到解题页**
          （D24）——「这一步为什么这么走」本来就挂在难度和知识点上，讲的时候收起来等于让人靠记忆
      ↓
④ 【双模式选择】 ← D9
      ├──「直接看答案」→ direct 模式：**走独立链路**（D15）——
      │      不进引导引擎、不生成引导地图、无快捷动作；
      │      一轮直出「答案 + 完整解析 + 考什么 + 易错点」→ 会话直接置 solved
      └──「引导我解」  → guide 模式 ↓
      ↓
⑤ 【引导地图生成 + 迈出第一步】← D10 / D11（本轮重点）
      5.1 模型先完成**完整分析**，一次性产出"引导地图"：
          · 解题步骤骨架 steps（3~6 步）
          · 每一步的 analysis（考什么、为什么这么做）+ approach（怎么下手）← S0 默认给
          · 每一步的 ladder：S1 具体方法 / S2 算式结构 / S3 单步演示
          · 整体解题路线预告 route_preview（只说"怎么走"，不说"怎么做"）
          · 备选解题路径 alt_routes（主路径走不通时换哪条）
          · 易错点预判 pitfalls
          · 标准答案 answer（仅内部校验，永不展示）
      5.2 地图落库到 sessions.plan（后续每轮都从这里取"当前步 + 该步强度"，不再重复分析）
      5.3 只展示第一步：路线预告 + 第一步的分析与思路 + 状态徽标 + 分步进度 → 等待学生输入
      ↓
⑥ 学生输入自己的思路 / 答案
      ↓
⑦ AI 判定状态 → 给针对性反馈 → 再走一小步
      ├── CORRECT  → 具体肯定对在哪里 + 把下一步方向交给他
      ├── WRONG    → 指出这一步的**具体错因**（符号/条件/单位/概念）+ 更强支持
      ├── STUCK    → 🔴 **直接给这一步的分析 + 解题思路**，再给一个具体小动作
      │              （绝不回"你再想想"——这是本产品最不能出现的回复）
      ├── ASK_WHY  → 正面回答"为什么"，不许反问回去
      └── WANTS_ANSWER → 先给足分析与思路，再说明为什么不给最终结论
      ↓
⑧ 循环 ⑤~⑦，直到 is_solved = true
      ↓
⑨ 收尾：完整解析 + 知识点总结 + 易错点（+ 同类题推荐，Phase 3）
```

### ⑤ 引导地图（Guide Map）—— 一次分析，全程复用　← D10 / D11

**问题**：如果每轮都让模型"现想现引导"，会出现三种典型翻车：
① 引导方向前后不一致；② 前几步说完发现后面走不通；③ 学生卡住时模型只会重复同一句话。

**解法**：把"分析"和"引导"彻底分开。
进入引导模式的第一步，模型**不输出引导语，先输出一张完整的引导地图**；拿到地图后才迈出第一步。

```
analyze（一次，成本高）
  └──▶ Guide Map 落库 sessions.plan
             │
             ├── steps[]        解题步骤骨架（3~6 步）
             │     ├── analysis   这一步在考什么、为什么这么做      ← S0 用
             │     ├── approach   这一步该怎么下手（方向 + 理由）    ← S0 用
             │     └── ladder     S1 / S2 / S3 三档更具体版本
             ├── route_preview  整体解题路线预告（对学生可见，只说走向）
             ├── alt_routes[]   备选解题路径（主路径走不通时换哪条）
             ├── pitfalls[]     易错点预判（收尾报告用）
             └── answer         标准答案（仅内部校验用，永不展示）

每轮对话（多次，成本低）
  └──▶ 只做三件事：判定状态 → 从当前步取合适强度（S0~S3）→ 结合学生原话改写成引导
```

**Guide Map 数据结构**

```json
{
  "steps": [
    {
      "index": 1,
      "goal": "把原式整理成顶点式所需的标准形",
      "analysis": "这一步要把式子变成能直接读出顶点坐标的样子。顶点式的好处是横纵坐标一眼可见，所以这类求最值的题都先走这一步。",
      "approach": "目标是凑成完全平方。x² - 6x 这部分用配方就能变成 (x - 3)² 的形式，先只处理它。",
      "ladder": {
        "S1": "配方时给 x 的系数一半、再平方。这题 x 的系数是 -6，一半就是 -3。",
        "S2": "把式子写成 y = (x - 3)² - 9 + c 的样子，你只算括号里的和修正项。",
        "S3": "完整演示：x² - 6x = (x - 3)² - 9，所以原式可以写成……（演示到此，停下提问）"
      },
      "common_wrong": ["配方时忘记减去平方出来的常数，导致式子变形后不等价"]
    }
  ],
  "route_preview": "这道题咱们分三步走：先把式子整理成顶点式，再读出最低点，最后回答题目问的那个量。",
  "alt_routes": [
    {
      "name": "公式法",
      "when": "学生配方反复出错，但对公式记忆牢靠",
      "steps": ["用 -b/2a 求顶点横坐标", "代回求纵坐标", "写出结论"]
    }
  ],
  "pitfalls": ["配方时漏减常数项", "把顶点横坐标当成顶点坐标"]
}
```

**五条硬性规则**

| 规则 | 说明 |
|------|------|
| 分析前置 | 引导模式的第一轮必须先出地图，不允许"边聊边分析"。未拿到地图前不进入对话循环 |
| **每步自带分析与思路** | 地图里每一步都存 `analysis`（考什么、为什么）+ `approach`（怎么下手）。**这是 S0 的默认输出，学生一卡住就直接给他讲**，不需要重新调用模型推理 |
| **路径预告只说走向** | `route_preview` 可以讲"分几步、每步干什么"（让学生知道这条路走得通、降低畏难），**但不能讲任何具体做法、公式或数值** |
| 路径预告只出现一次 | 仅第一轮展示；之后每轮只聚焦当前步，避免每轮重复造成噪音 |
| 阶梯是上限也是下限 | 每轮 `support_level` 必须落在当前步的 `ladder` 之内；一次最多升一级，**禁止跳级**（S1 直接跳到 S3） |

**为什么 `analysis` / `approach` 必须进地图（v0.3 的核心修正）**

用户明确指出：**学生说"不会做"时只回一句"你再想想"是弱智设计。**

- 学生卡住时缺的是**思路**。如果不预先在地图里备好每步的分析与思路，
  模型在对话轮里就很容易滑向"你自己再想想"这类零信息回复。
- 把 `analysis` / `approach` 写进地图，等于**强制模型在备课阶段就把思路想清楚**，
  对话轮只是把它讲出来。这从结构上杜绝了空泛回复。
- 因此 `analysis` / `approach` 的**具体度**必须校验（P8）：
  像"考查二次函数的性质"这种空话判不合格，要求重生成。

**「备选解题路径」的触发条件（alt_routes）**

引导不是一条直线。当学生的思路与主干路径持续冲突时，换成更贴合他的那条路：

| 触发 | 动作 |
|------|------|
| 学生连续 2 轮 `STUCK` 且当前路径的 S2 算式结构也没能让他动起来 | 切到 `alt_routes` 里最贴合学生已表现出的能力的那条，并明确告诉学生"咱们换条路试试"（换路后**立刻给新路径第一步的分析与思路**，不能只宣布换路） |
| 学生自己提出了一条合理的不同解法 | **跟随学生的思路**，不强行拉回主干路径；把学生的路径临时登记为新的 `alt_routes` |
| 学生连续 2 轮 `WRONG` 且错因相同 | 不要退回 S0 把同一套话再讲一遍，换一条路径重讲同一个目标 |

> 🔴 红线不变：无论走主干还是备选路径，**都不输出最终答案**。
> 换路径只换来"更合适的引导方式"，不换来"更接近答案的捷径"。

**性能收益（顺带解决的两个问题）**

1. **省 token**：分析只做一次，每轮对话只需带"当前步 + 该步阶梯 + 最近 N 轮"，上下文长度可控（对应风险 R2）。
2. **快响应**：`step_ladder` 随第一轮一起下发给前端并缓存在本地。
   学生点「再讲细一点」时，前端可**先用本地阶梯文案即时响应**（< 200ms），
   同时在后台请求模型生成一版贴合学生原话的改写并替换——兼顾"秒回"与"不机械"。

### 过程内快捷按钮（D9 后半部分）

| 按钮 | 行为 | 映射 |
|------|------|------|
| 再讲细一点 | 提升一级 `support_level`（S0→S1→S2） | `POST /sessions/:id/hint { action: "MORE_DETAIL" }` |
| 为什么这么做 | 触发 `ASK_WHY`，**正面讲清原因**，不许反问回去 | `POST /sessions/:id/hint { action: "EXPLAIN_WHY" }` |
| 直接讲这一步 | `support_level` 置为 S3，仅演示当前一步 | `POST /sessions/:id/hint { action: "EXPLAIN_THIS_STEP" }` |
| 我自己再想想 | 不给提示，仅记录 | 纯前端，不发请求 |

> - 按钮由模型在 `quick_replies` 字段里动态给出，不写死。学生在按钮之外仍可自由输入。
> - 「我自己再想想」是**学生主动选择**才出现的，AI 不得把它当成对学生"不会"的回应
>   （即：学生说不会时，AI 不能回一句"那你再想想"）。这条在提示词里已列为红线。

### 双模式与红线的边界

- `guide` 模式：**永不出现最终答案**（红线不变）。
- `direct` 模式：可直出解析与答案，但会话上必须留下 `mode = direct` 标记，
  便于 Phase 3 家长报告区分"看了答案"与"自己解出"。
- 模型在 `guide` 模式下若被反复索要答案，可提示学生切换到 `direct` 模式——
  切换动作由学生主动完成，AI 不代替学生做这个决定。

## 接口设计

统一前缀 `/api`，返回结构 `{ ok: boolean, data?: T, error?: { code, message } }`。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/health` | 健康检查 |
| GET | `/api/config` | 读取运行时配置：是否已接入模型、脱敏后的 Key、当前模型名、控制台地址 |
| PUT | `/api/config/api-key` | 保存 Key：写入 `server/.env` 并热更新到当前进程（**仅环回 / 私网来源可调用**） |
| POST | `/api/config/verify` | 连通性自检：用 VL 模型发一次最小请求，返回可读结论与耗时 |
| POST | `/api/problems` | 上传图片（multipart），创建题目，返回 `problemId` + 识别结果 |
| GET | `/api/problems/:id` | 题目详情（含识别文本、学科、知识点） |
| PATCH | `/api/problems/:id` | 学生修正识别文本/学科，重新分析 |
| POST | `/api/problems/:id/analyze` | 重新分析：产出**引导地图**（步骤骨架 + 提示阶梯 + 路径预告 + 备选思路 + 易错点），写入该题目的最新分析结果 |
| POST | `/api/sessions` | 创建解题会话 `{ problemId, mode: "guide" \| "direct" }`；guide 模式会**先做一次分析前置**，产出引导地图后才返回（这一步耗时较长，前端需给"老师正在备课"反馈） |
| POST | `/api/sessions/:id/start` | **首轮引导**：路径预告 + 第一步引导，SSE 流式返回 |
| GET | `/api/sessions` | 历史会话列表（分页） |
| GET | `/api/sessions/:id` | 会话详情 + 全部消息 |
| POST | `/api/sessions/:id/messages` | 学生输入，**SSE 流式**返回 AI 引导 |
| POST | `/api/sessions/:id/hint` | 快捷动作：`MORE_HINT` / `EXPLAIN_THIS_STEP` / `SHOW_ANSWER` |
| POST | `/api/sessions/:id/finalize` | 生成完整解析 + 知识点 + 易错点 |
| DELETE | `/api/sessions/:id` | 删除会话（Phase 2） |

### 核心接口：`POST /api/sessions/:id/messages`

请求：

```json
{
  "content": "我把 -b/2a 算成 3 了",
  "type": "text"
}
```

SSE 流式响应（事件类型）：

```
event: meta
data: {"state":"PARTIAL","supportLevel":2,"stepIndex":1,"totalSteps":3,
       "stepGoal":"把原式整理成顶点式所需的标准形",
       "routePreview":null,
       "stepLadder":null,
       "canSwitchRoute":false,
       "quickReplies":["再讲细一点","为什么这么做","我自己再想想"]}

event: delta
data: {"text":"这一步其实是在考你怎么看出函数的最值——"}

event: done
data: {"messageId":"m_123","isSolved":false}
```

> - `supportLevel` 为 **0~3**：0 = 分析 + 思路（默认档），1 = 思路 + 具体方法，2 = 方法 + 算式结构，3 = 单步演示。
> - `routePreview` **仅第一轮**非 null（整体路线预告只出现一次）。
> - `stepLadder` **仅第一轮**下发当前步的 S1~S3，前端缓存用于「再讲细一点」的即时响应。
> - `canSwitchRoute` 为 true 时前端展示「换个思路试试」按钮（对应 `alt_routes` 备选路径逻辑）。
> - `meta` 先于 `delta` 下发，前端可据此先渲染状态徽标与快捷按钮，正文再逐字出现。

## 数据模型

使用 Drizzle ORM，字段命名 camelCase ↔ 数据库 snake_case。

### problems（题目）

### messages（对话消息）

### knowledge_points（知识点，Phase 2）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | text PK | — |
| subject | text | 学科 |
| name | text | 知识点名称 |
| parentId | text | 支持层级（如 函数 → 二次函数） |

> 避免过度设计；Phase 2 做标签统计时再迁移。

### 附：D25 作答框方案（⏳ 待确认，确认后再动手）

**目标**：学生能写出 `f'(x) = 1 - 1/(ax)` 这种式子，并**一眼看见它排好版的样子**；
导入方式必须是「点一下」，**不是「学语法」**。

**四个组成部分**

| # | 组成 | 说明 |
|---|------|------|
| 1 | **输入区换成 contenteditable** | 沿用 `ProblemEditor` 已有的模型（文字正常打字换行 / 公式是 `contenteditable=false` 的 KaTeX 卡片、在编辑区里是一个原子）。抽成共用组件 `RichMathInput`，题干编辑器与作答框都用它 |
| 2 | **符号条**（新增） | 输入区上方一排可横向滚动的按钮，点一下在光标处插入一条公式卡片。首期 12 个：`a/b` 分数、`x²` 指数、`xₙ` 下标、`√`、`≤`、`≥`、`≠`、`π`、`∞`、`ln`、`f'` 导数撇、`→` |
| 3 | **卡片面板** | 复用 `ProblemEditor` 的交互：大号 KaTeX 渲染图 + 实时预览 + 整条输入框。面板里**再放一排同样的符号按钮** —— 改公式的时候不该逼人切回键盘找符号 |
| 4 | **选择即包裹** | 输入区里选中一段文字再点符号条，直接包进去：选中 `2` 点 `√` → `\sqrt{2}`。这是标准编辑器行为，比"插空模板再填"少两步 |

**两个必须一起改的地方（否则功能是残的）**

- 🔴 **学生消息气泡现在不渲染公式**：`ChatBubble` 的 `isUser` 分支直接输出 `{message.content}`，
  发出去的 `$x^2$` 会原样显示成 `$x^2$`。**输入时好看、发出去变回反斜杠**，比不做还糟 → 学生气泡改用 `MathText`。
- 🔴 **发送仍是 `$…$` 纯文本**：数据库列、接口、`tutor.system.md`、`answer.md` 全部不动。
  模型的对话里学生写过 `$…$` 是常态，本来就看懂。

**取舍（先说清楚代价）**

- **不做 MathQuill / MathLive**：它们能做到"光标在分数的分子分母之间跳"，体验最好，
  但体积 300KB+、手机软键盘适配差，且会和现有的 KaTeX 卡片变成两套渲染。
  代价是：**分数在编辑态是一张整体卡片，光标进不去里面**，改分数要打开面板。
- **写一条公式 ≈ 点按钮 + 改字 + 回车**，比手写慢。所以符号条**只覆盖最常用的那十来个**，
  没覆盖到的（比如 `\int_0^1` 这种）鼓励学生**直接用文字说**（"从 0 到 1 积分"）——
  引导模式本来就是对话，不是交作业。
- 已知风险：`contenteditable` 在**中文输入法**下的组合输入（拼音串）行为，手机端需要真机验证一次；
  若出现掉字，退路是输入区退回 `<textarea>`、只保留符号条插入 + 发出去渲染。

**待你拍板的两点**：① 符号条这 12 个够不够 / 要不要换；
② 上面那条代价（写公式比手写慢）能不能接受 —— 如果觉得得不偿失，我改成"输入区不渲染、
只保证发出去的气泡渲染"这一档，改动量会小很多。

### 附：D26 深度思考的实测数据与实现要点（⏳ 待确认）

**环境**：`qwen3.8-max` + `answer.md`（1590 字）+ 库内第一道题（题面 177 字），`temperature: 0.3`，流式。

| 配置 | 首个正文片段 | 总耗时 | 思考字数 | 正文字数 | completion tokens |
|---|---|---|---|---|---|
| **开思考**（官方默认） | **207.0s** | 242.3s | 27317 | 3316 | 11887（其中 `reasoning_tokens` 9808） |
| **关思考** | 0.44s | 109.1s | 0 | 10986 | 6772 |

⚠️ 两次调用的正文长度差很多（3316 vs 10986 字），**单次样本不足以断言"平均快多少"**；
但方向是确定的：**思考会显著推迟第一个正文字，并吃掉 80% 以上的输出 token**。
另外历史 direct 会话在库里的耗时是 20~35s（`created_at` 差值）—— 波动极大，说明
**该盯的指标是「第一批内容多久出现」，而不是「总耗时」**。

**实现要点**

1. `server/src/providers/types.ts`：`ChatOptions` 增加 `thinking?: boolean`
2. `server/src/providers/openaiCompatible.ts`：`buildBody` 透传 `enable_thinking`；
   `extractDelta()` 从返回 `string` 改成返回 `{ content, reasoning }`；
   `chatStream()` 的 yield 类型随之变成结构体 —— **所有调用方都要跟着改**
3. `shared/src/types.ts`：新增 `thinking` SSE 事件（与 `delta` 并列）；
   前端 `useTutorSession` 累积思考文本
4. 前端：气泡内**可折叠思考区** —— 生成中默认展开、实时滚动、显示「正在思考…」+ 已思考字数；
   正文一出现自动收起成一行「已思考 3 分 27 秒」
5. **思考不落库**：不写进 `messages`。刷新或回看历史时没有思考区 —— 这是有意的，
   正文里的答案与解析才是要留下的东西
6. ⚠️ **待测风险**：`response_format: json_object` 与思考模式在百炼上的兼容性
   （`analyze` / `plan` / `tutorEngine` 三处调用都带 `json: true`）。
   若不兼容 → 这三处保持 `thinking: false`，只有面向学生的正文（`direct` / `summarize`）开思考

**为什么"显示"比"加速"更值**：开思考时界面会有 3 分半完全空白，
用户唯一能做的判断是"它是不是卡死了"。思考接出来之后，**第 0.7 秒屏幕上就有字在动**。
